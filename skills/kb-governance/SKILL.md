# 知识库治理闭环（体检 → 规整 → 复核 → 复审）

> 方法论源自 MUYI 全库治理实战（2026-10）：359→342 篇，行文违规降 84%，技术矛盾清零，
> 全程结构无损、构建全绿。目标：让知识库"每篇可信、互相链接、行文统一"。

## 前置：明确治理边界

- 库路径（默认参数或用户指定）；先跑一次构建确认基线是绿的
- **记录基线快照**：md 总数、链接总数、来源标注数、代码块数、README 计数——治理全程这些结构指标必须零损伤

## 第一阶段：体检（audit）

跑姊妹技能 `kb-upkeep` 的 `scripts/audit.sh [库路径]`，产出五类报告：
空壳文档 / 链接占位 / 外链图片测活 / 库内相对死链 / 结构统计。
本阶段只收集问题清单，不修改内容。

## 第二阶段：规整（normalize · STC 行文规约）

目标：全库统一为简化技术中文（STC）行文，消除文体性违规。

1. **引入规约 skill**：检索并采用 simplified-technical-chinese（或库内已有规约文档）作为判据
2. **分波并行**：按 20 篇/子代理分波（4 波起），每波产出违规清单 + 修复 diff；**必须级违规**（长句堆叠、冗词、"我们可以看到"式口水）优先于**建议级**（句式多样性）
3. **体裁豁免**：面试问句、对话体、引用原文不按 STC 判——豁免清单显式记录，不算残留
4. **结构零损伤铁律**：链接、来源标注、代码块、frontmatter 原样保留；每波结束抽查 diff 确认未误伤
5. 产出：违规数前后对比（目标降幅 80%+）、豁免清单

## 第三阶段：复核（review · 内容质量）

换用审稿视角的 skill 作"检索编辑人"（technical-documentation-review / reviewing-article / cold-reading-documents 或同级），逐篇过三类判断：

1. **判合并**：同主题双胞胎文档（如 HashMap/Hashtable 式）合并为一篇，保留双标题重定向链接
2. **判冗余**：空壳、死水（半年无链接指向且内容单薄）、纯链接占位——删除并记录清单
3. **判质量**：技术矛盾逐条修正，**面试硬伤最高优先**（概念张冠李戴、结论颠倒这类会被面试官抓的）

每轮"审查 → 整改 → 记录"一体，一类问题一个 commit。

## 第四阶段：复审（re-check · 换场景验证）

用**没有参与前几轮的代理**（避免确认偏误）做三件事：

1. **防静默丢失**：对合并/删除的文档逐篇 `git show <旧commit>:<路径>` 比对源文件，找回合并时静默丢失的整节内容
2. **冷读场景测试**：抽高流量文档 5-8 篇，模拟真实任务（"30 分钟面试冲刺/oncall 排障"）走一遍，检验答案链是否完整、有无断链依赖
3. **全局清扫**：死链归零复查、删历史空图片引用、修假标记（如自测清单里指向不存在文章的🕳）

## 验收标准（收尾必查）

1. 重跑 audit：空壳 0 / 占位 0 / 相对死链 0
2. 结构指标与基线快照一致（链接/标注/代码块无净损失，减少项均有删除记录对应）
3. 构建全绿（VitePress/其它）
4. README 与自测清单计数同步
5. git log 符合"一类一 commit"；治理报告（违规前后、合并/删除清单、矛盾修复清单）交付用户

## 治理报告模板

```
治理对象：库名 @ commit
基线 → 终态：N 篇 → M 篇 ｜ 违规 X → Y（降 Z%）
合并：n 组（列表） ｜ 删除：m 篇（列表）
矛盾修复：k 处（面试硬伤标注） ｜ 静默丢失找回：p 处
结构指标：链接 a→a ｜ 标注 b→b ｜ 构建 ✓
```
